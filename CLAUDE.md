# CLAUDE.md — Climate Analytics Platform

## What This Repo Is

A climate analytics platform: a monthly-refreshed data pipeline, a FastAPI backend, a React + TypeScript
dashboard built on `@syena/ds`, an MCP server, and a LangGraph agent. The analysis notebooks are the
modelling layer whose computations the API mirrors. Each sub-project has its own documentation:
[`SPEC.md`](SPEC.md) for the dashboard and API, [`services/mcp-server/SPEC.md`](services/mcp-server/SPEC.md)
for the MCP server, and [`services/agent/SPEC.md`](services/agent/SPEC.md) for the LangGraph agent built on it.

Contains:
- `notebook/week1_eda.ipynb` … `notebook/week5_scenarios.ipynb` — one notebook per week (split from the original single combined notebook); each runs independently, loading CSVs saved by the previous week
- `notebook/constants.py` — shared constants (`FEATURED_COUNTRIES`, `NON_SOVEREIGN`, `FEATURES`, `TARGET`, `TRAIN_CUTOFF`, `FORECAST_END`, etc.) imported by every week's notebook via `from constants import *` — single source of truth, do not redefine these inline in a notebook
- `notebook/archive/ghg_analysis_combined.ipynb` — the original all-in-one notebook, kept only as an inert backup; not maintained, not referenced by docs
- `app.py` — Streamlit dashboard, an alternative front end to the React dashboard
- `api/` — FastAPI backend, exposing the same page computations as JSON for `climate-dashboard-react/`; mirrors `app.py`'s pandas logic 1:1 endpoint-by-endpoint, `@lru_cache` in place of `@st.cache_data`. Has a pytest suite (`api/tests/`, run via `pytest api/tests`) covering every endpoint's happy path, 4xx/503 error paths, and pandas edge cases, against fixture CSVs written to a temp dir rather than the real (gitignored) data
- `climate-dashboard-react/` — React + TypeScript dashboard consuming `api/`, built on `@syena/ds`, the Syena design system (a separate, sibling checkout at `../syena-design-system` relative to this repo — not part of this monorepo since it is shared across other projects too; the Vite, Vitest and tsconfig aliases in `climate-dashboard-react/` point at its `src/`, and `SYN_DS_PATH` overrides the location). Has a Vitest + React Testing Library suite (`npm test`) — API client tests plus a loading/data/error smoke test per page; `Chart` is stubbed in page tests since Plotly's DOM lifecycle is the design system's own test suite's concern, not this app's
- `services/mcp-server/` — MCP server wrapping `api/` as hand-curated MCP tools for Claude Desktop/Code and, later, a LangGraph agent — Stage 1 of a separate conversational-agent project. Independently versioned/deployable from `api/` (own `pyproject.toml`), calls `api/` over HTTP like any other consumer, not a shared-library import. Own [`CLAUDE.md`](services/mcp-server/CLAUDE.md), [`SPEC.md`](services/mcp-server/SPEC.md) — see those rather than this file or the root `SPEC.md` for its design
- `services/agent/` — LangGraph conversational agent, surfaced as a new nav item in `climate-dashboard-react/` — Stage 2 of the conversational-agent project `services/mcp-server` began. Calls `services/mcp-server`'s tools as an MCP client (`langchain-mcp-adapters`), unauthenticated over localhost since it's co-located with `services/mcp-server` on the same deploy host; renders results as real `@syena/ds` components, never generated markup. Independently versioned/deployable (own `pyproject.toml`). Also hosts this repo's first admin-panel capability (LLM provider/model switching) — see the "Admin capabilities" note below. Own [`CLAUDE.md`](services/agent/CLAUDE.md) and [`SPEC.md`](services/agent/SPEC.md) — see those rather than this file for its design and node catalog
- `data/` — gitignored CSVs; the OWID dataset is downloaded manually, all other CSVs (`ghg_filtered.csv`, `ghg_features.csv`, `model_comparison_regression.csv`, `ets_forecasts.csv`, `model_comparison.csv`, `scenario_projections.csv`) are regenerated locally by running the week notebooks in order
- `requirements.txt` — pinned Python deps (pandas, scikit-learn, statsmodels, streamlit, fastapi, uvicorn, etc.) — shared across the notebooks, `app.py` and `api/`

**Admin capabilities (cross-cutting).** A single Cloudflare Access-gated admin surface (login
policy, Google as identity provider, one allow-listed account) spans multiple sub-projects rather
than living inside any one of them — see [`ARCHITECTURE.md`](ARCHITECTURE.md) §8 for the shared
Access-application/path-rule convention and the "each service owns its own admin routes, no
shared admin service" rule. Today's only capability, LLM provider/model switching, lives entirely
in `services/agent` — see its own [`SPEC.md`](services/agent/SPEC.md).

## Key Design Decisions

- **Forecasting model: ETS(A,Ad,N) — Holt's Damped Trend (statsmodels `ExponentialSmoothing`), NOT Prophet and NOT ARIMA.** Prophet is inappropriate for annual data. ARIMA was the original choice but was replaced: the damped trend in ETS(A,Ad,N) prevents unbounded long-range extrapolation and better captures emissions slowdowns in developed countries (UK, Germany). Implemented via `ExponentialSmoothing(train, trend='add', damped_trend=True, seasonal=None)`.
- **Random Forest: two variants in Week 3 plus a recursive forecast in §3.8.** §3.5 trains RF per country (~25 rows each, bare `FEATURES`) — intentionally included to demonstrate overfitting on small data; do NOT add `country_encoded` here. §3.6 trains a single pooled RF on all expanded countries combined with `country_encoded` (via `LabelEncoder`) as an additional feature — this is the production approach. The encoder must be **fitted on the full `get_expanded_countries()` list** (not `FEATURED_COUNTRIES`, since the expanded set was introduced — see the two-tier country pattern below) and the same fitted object reused to transform test rows — never refit on test data. `country_encoded` is **§3.6 RF-only**: do NOT add it to the shared `FEATURES` constant (used by LR and §3.5 RF-PC); use `RF_FEATURES = FEATURES + ['country_encoded']` exclusively for §3.6 and §3.8. Both RF variants are evaluated per country; all four models (Baseline, LR, RF-PC, RF Pooled) appear in the §3.7 comparison table. The mandatory limitations cell explaining why pooling is necessary sits immediately before the §3.6 code cell.
- **§3.6 RF Pooled extended training data.** `rf_model` is trained on `_train_ext` — built inline in §3.6 by loading raw `owid-co2-data.csv` back to `year >= 1975` and computing features on the fly. This gives ~1,600 training rows (1979–2018, ~40/country at the expanded scale) vs the original ~250 rows (1994–2018, ~24/country, 10 countries). LR uses `train` (from `ghg_features.csv`, year ≥ 1990) and ETS uses `df_filtered` — both unchanged. Do NOT change their data sources. Originally validated via `experiment/1980-start` branch at the 10-country scale: RF Pooled MAE improved for all 10 countries; LR and ETS worsened for most.
- **§3.8 RF Pooled Recursive Forecasts to 2043.** Uses the already-fitted `rf_model` and `le` from §3.6 to recursively forecast from 2019 to 2043 for all expanded countries. LR is excluded from §3.8: per-country LR models predict negative CO₂ for declining-trend countries (UK, Germany, Japan), which feed back as lag values and cause rapid numerical divergence. RF's bounded predictions (capped by training range) remain stable over the 25-step horizon. The plot itself stays a 5×2 grid over `FEATURED_COUNTRIES` only (matching §4.3) — see the two-tier country pattern below for why the grid doesn't scale with the underlying data.
- **Train/test split:** 1990–2018 train, 2019–2023 test. This captures the COVID-19 emissions dip in 2020 in the test set.
- **Two-tier country pattern:** `FEATURED_COUNTRIES` (10, hardcoded — China, USA, India, Russia, Japan, Germany, Brazil, UK, South Africa, Australia) is the original curated set, still used as the default/narrative selection everywhere (fixed-size 5×2 subplot grids, seeded dropdown defaults). A `get_expanded_countries()` function — defined independently in `notebook/constants.py` and `app.py`, and as `load_expanded_countries()` in `api/data_loaders.py` — loads a data-driven set of ~40 major emitters (coverage + materiality thresholds, computed in Week 1 §1.2, persisted to `data/selected_countries.json`), used everywhere else: per-country training/evaluation loops, aggregate sums, tables, and any interactive picker's searchable pool. The notebook version raises `FileNotFoundError` uncaught (Weeks 2–5 can't proceed without it); the `app.py`/`api` versions degrade gracefully, falling back to `FEATURED_COUNTRIES` with a warning instead of crashing. Multi-country pickers that feed a chart (React `MultiSelect`, Streamlit `st.multiselect`) cap simultaneous selections at 10 even though their searchable pool is the full expanded list — past 10 countries on one chart stops being readable. **The Overview page (`SPEC.md` §5.7) extends this into three simultaneous tiers** instead of picking one: "All Countries" (every sovereign country, `NON_SOVEREIGN` excluded, unfiltered by coverage/Mt), "Expanded" (the ~40-country set above), and "Selected" (a user-picked subset capped at 10, defaulted to `FEATURED_COUNTRIES`) — only the Selected tier drives the bar chart/% change chart/Top Movers.
- **Scope:** Classical ML only (Linear Regression, Random Forest, ETS). No deep learning or LLMs — intentional to keep the scope manageable.
- **Week 5's BAU is a second ETS(A,Ad,N) fit on all observed years (1990–2024), not Week 4's forecast.** Week 4's fit stops at 2018 (`TRAIN_CUTOFF`) purely so 2019–2023 can be held out for evaluation; reusing it as the scenario baseline started the scenarios +3.7% above the observed 2024 total. Week 4 is unchanged (do not move its cutoff); Week 5 fits its own baseline and does not read `ets_forecasts.csv`. `SPEC.md` §6.2. `pipeline/ets_baseline.py` is an independent implementation for Area 2.

## When Helping With This Project

- Reference the design decisions above before suggesting model or methodology changes.
- For detailed requirements, refer to [`SPEC.md`](SPEC.md).
- Analysis code lives in the notebooks (`notebook/week1_eda.ipynb` … `notebook/week5_scenarios.ipynb`, run in order), with shared constants in `notebook/constants.py`; `app.py` is the Streamlit dashboard.
- The `data/` CSVs are not committed — download the OWID dataset per README instructions and regenerate the rest by running the notebooks in order.
- Notebooks are committed without outputs or execution counts; a test (`notebook/tests`) and the data refresh keep it that way (see "Notebook outputs" in `README.md`).
- When implementing notebook work that is broken into sections, use a feature branch **per section**: branch → implement → commit → push → open PR → review → merge → move to the next section, so each review is a small diff rather than one large one.
- Avoid suggesting Prophet, deep learning, or LLM-based approaches — out of scope by design.
